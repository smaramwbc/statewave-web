Yesterday I ended with:

> Can verified product knowledge become a complete user task — without giving the model any new authority?

Turns out:

**yes.**

And the bug was almost embarrassingly simple.

Statewave Guide already knew:

- there is a **Rotate API key** control
- there is an **Export CSV** control
- there is a **Delete** control
- these controls belong to specific verified workflows

Yet the guidance still looked like:

> Open Settings.

or:

> Open Clients.

Why?

Because some workflow steps pointed to:

```text
feature:<id>
```

A feature is not necessarily a button.

The Guidance Compiler expected an actionable graph node.

Couldn't resolve one?

Drop the action.

Silently.

Which is how perfectly verified knowledge somehow became a very polite dead end.

So we added another layer:

<Flow steps={['Verified feature', 'Resolve actual action target', 'Prove it belongs to the feature', 'Prove the user can act on it', 'Emit the step']} />

And importantly:

> **A feature reference is not a control.**

Obvious now.

Apparently less obvious to the compiler. 😄

We also started measuring task completeness properly:

<Flow steps={['Entry', 'Task action', 'Terminal action', 'Complete path']} />

So:

> Open Settings.

is no longer allowed to congratulate itself for being an actionable workflow.

Then we reran the same benchmark.

Useful outputs:

**33% → 67%**

Actionability:

**1.14 → 1.52 / 2**

Real task actions started surviving compilation.

But we were still just below the gate.

Then one tiny case exposed the next problem.

The Settings form.

We knew:

- the form exists
- **Save changes** exists
- both reach the same verified submit surface

But because the actionable control wasn't structurally owned exactly the way the compiler expected, we still produced:

> Open Settings.

So we introduced one deliberately narrow recovery rule:

<Flow steps={['Passive feature', 'Verified shared action surface', 'Exactly one valid actionable control', 'Recover it']} />

No proximity guessing.

No:

> “That button looks about right.”

No model interpretation.

Just evidence.

The result:

> Open Settings.  
> Choose “Save changes”.

Two outputs changed.

**19 stayed exactly the same.**

The benchmark moved from:

**14 / 21 useful**

to:

**15 / 21 useful**

**71.4%**

For the first time:

**Development usefulness gate: PASS ✅**

Median usefulness:

**2 / 3**

Incorrect factual claims:

**0**

That last number still matters more to me than the pass.

Because we could have made the system look smarter much earlier by letting the model fill gaps.

We keep refusing to do that.

Two plausible actions?

Refuse.

A feature with no provable control?

Refuse.

A control exists but we can't prove it belongs to the task?

Refuse.

So the lesson became:

> **Resolvable is not the same as sayable.**

And:

> **The system shouldn't become more useful by becoming less trustworthy.**

We crossed the usefulness gate without giving the model a single extra bit of factual authority.

Which felt great.

For approximately five minutes.

Then we looked at some explanatory sentences:

> “for an account manager”

> “without leaving the page”

> “onto the enterprise plan”

Reasonable.

Plausible.

Not necessarily provable.
